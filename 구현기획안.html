닉네임이나 방 코드까지 로컬에 넣으면 서버와 어긋난다. user_id 하나만 있으면 나머지는 서버에서 다시 받으면 된다.

let id = localStorage.getItem('user_id')
if (!id) {
  id = (await post('/users')).user_id
  localStorage.setItem('user_id', id)
}

새로고침 복구

F5 또는 모바일 브라우저가 탭을 죽였을 때

localStorage에서 user_id 읽음
   → GET /users/me?user_id=...        닉네임 · 성별 복원
   → GET /rooms/{code}                현재 단계 복원
   → 그 단계부터 이어서 진행
전화를 받다가 탭이 죽는 건 흔한 일이다. 이게 없으면 세션 중 새로고침 한 번에, 서버에 데이터가 멀쩡히 있는데도 다시 못 붙는다.

user_id를 잃는 경우

브라우저 데이터 삭제 · 다른 기기 · 시크릿 모드. 이러면 새 사람으로 시작된다.
MVP에서는 복구하지 않는다. 복구 링크나 계정 연동은 만들지 않는다. 트러블슈팅 문서에만 적는다.

로그인 없는 서비스가 그 이상을 보장하는 경우는 드물다. 복구는 P1에서 로그인을 붙이면서 해결한다. 그때 익명 user_id를 그대로 승격하면 데이터가 안 깨진다.

05 · Types

유형 — 공통 3축으로만 뽑는다

DOM ≥ 2.5 ? 상 : 하
PLN ≥ 2.5 ? 상 : 하        →  2 × 2 × 2 = 8분면
EXP ≥ 2.5 ? 직구 : 변화구

점수 자체는 안 쓴다. 2.5를 넘었냐 아니냐만 본다. 세 축 중 하나라도 2.5 ± 0.3 안이면 SPD로 가르는 타이브레이크가 작동한다.

왜 이 3개인가

뺀 축이유
SPD 속도DOM과 상관이 너무 높다. 끌고 가는 사람은 대개 빨리 지른다
OPN 개방성눈에 안 보인다. 게임 한 판으론 안 드러난다
EMP 공감문항을 잘못 짜면 전원이 높게 답한다. 3지선다로 갈리게 만들 수는 있지만(§08) 유형 축으로 쓰기엔 여전히 불안정하다
8개가 한계다. 축을 4개 쓰면 16유형, 5개면 32유형이다. MBTI가 16개인데 그것도 이미 많다. 한 세션에 6명이 서로 유형을 보여주며 웃어야 하는데, 32개면 남의 유형이 뭔지 감이 안 온다. 8개여야 "아 쟤 그거구나"가 된다.

② 칭호 일부      "팀의 평균값" "극단주의자"는 9축 전체를 봄
③ 리포트 서술    LLM이 인용하는 디테일 ← 실질적으로 가장 중요

1. 리커트 금지. 대신 세 형식을 허용한다 (D19)
   ✗ "1~5점으로 답하세요"  "얼마나 그런가"     ← 추상적 자기평가. 3~4에 몰린다

   ✓ 3지선다        축이 3단계로 자연스럽게 갈리는 상황
   ✓ 순서형 4지선다  시점 · 빈도 · 횟수처럼 자체 순서가 있는 것

   ✗ 4지 이상 비순서형                        ← 고를 근거가 없어 중간에 몰린다

2. 모든 선택지가 사회적으로 괜찮아야 한다
   ✗ A 계획을 세워서 한다   B 계획 없이 한다        ← 전원 A
   ✓ A 할 일을 먼저 쪼갠다   B 일단 해보면서 정한다   ← 갈린다

3. 성향을 묻지 말고 상황을 준다
4. 축당 2문항, 그중 1개는 역채점
   역채점 문항은 A 위치가 축의 0.0 쪽이다. 채점은 각 선택지 옆 부호를 따른다.
5. 한 문항은 한 축만 잰다
6. 카테고리 어휘를 쓴다
리커트는 추상적 자기평가를 숫자로 묻는다. 3지·순서형 4지는 구체적 행동을 고르게 한다. 중간 선택지도 실제 행동이라 정직하게 갈린다.

3지선다가 특히 원칙 2를 살린다. 2지선다면 착한 쪽으로 몰리는 문항도, 중간 선택지가 도피처가 아니라 가장 실용적인 대응이면 갈린다.
순서형 4지선다는 시점이 그 축의 의미와 직결될 때만 쓴다.
팀플 PLN에 "며칠 전부터 시작하나"를 쓰면 TP_DDL(마감 스타일)과 같은 걸 재게 된다. PLN은 "미리 정해두느냐 상황 보고 정하느냐" — 방식이고, TP_DDL은 "언제 하느냐" — 시점이다.
그래서 팀플 PLN은 2지선다, 낮 PLN은 순서형으로 갈렸다.

채점

2지선다      A +1        B −1
3지선다      A +1  B  0  C −1
순서형 4지    A +1  B +0.33  C −0.33  D −1

축 원점수 = 해당 축 문항 합계          범위 −2 ~ +2
SELF(axis) = (원점수 + 2) / 4 × 5      범위 0.0 ~ 5.0

두 문항이 부호가 반대로 강하게 갈리면 → 2.5, low_confidence = true

프롬프트 규칙 — 이 다섯 개를 반드시 넣는다

1. 넘겨받은 JSON에 있는 수치와 로그만 인용한다. 없는 사실을 만들지 않는다.
   ("회의에서 자주 발표하셨네요" 같은 문장 금지 — 그런 데이터가 없다)

2. 유형 · 칭호 · 궁합 등급은 이미 확정됐다. 바꾸지 않는다. 설명만 한다.

3. impression 값은 "팀이 본 나"다.
   "당신은 ○○입니다"로 쓰지 않는다. "팀은 당신을 ○○로 봤습니다"까지만.

4. 외모 · 성별 · 능력에 대한 문장을 만들지 않는다.

5. 개인 서술은 4~6문장. 궁합 이유는 1~2문장.
   수치를 최소 2개 인용한다. 인용 없는 뭉뚱그린 칭찬은 쓰지 않는다.

저장과 폴백

생성 성공 → DB 저장 → 이후 조회는 저장본만 읽는다
            └ LLM을 다시 부르지 않는다는 뜻이다. 저장은 반드시 한다
            └ 매번 부르면 같은 사람 리포트가 매번 달라진다

            └ 축 · 칭호 · 궁합은 룰 기반이라 그대로 채워진다
