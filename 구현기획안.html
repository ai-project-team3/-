NT_PCE(속도)를 뺐다. 공통 SPD와 같은 걸 재고 있었다.
SPD는 "재보고 간다 ↔ 일단 지른다"고 밤 라벨이 "속도가 빠르다"였다. 전용 축 NT_PCE도 "천천히 ↔ 빠르게"였다.
두 축이 같은 걸 재면 궁합 계산에서 그 방향이 이중으로 가중된다. 그리고 "속도"가 무엇의 속도인지 — 그날 진도인지, 관계 진전인지 — 읽는 사람마다 달라진다.
그래서 SPD 밤 라벨을 "망설이지 않는다" 로 못박고, 전용 축은 겹치지 않는 NT_MOD 분위기 의존도로 교체했다.
TP_CFL은 원래 회피/중재/직면 3분류였다. 축은 1차원이어야 하므로 회피↔직면으로 두고 2.5 부근을 중재형으로 해석한다. 리포트 문구에서만 "중재형"으로 표시한다.

04 · Types

유형 — 공통 3축으로만 뽑는다

DOM ≥ 2.5 ? 상 : 하
PLN ≥ 2.5 ? 상 : 하        →  2 × 2 × 2 = 8분면
EXP ≥ 2.5 ? 직구 : 변화구

점수 자체는 안 쓴다. 2.5를 넘었냐 아니냐만 본다. 세 축 중 하나라도 2.5 ± 0.3 안이면 SPD로 가르는 타이브레이크가 작동한다.

왜 이 3개인가

뺀 축이유
SPD 속도DOM과 상관이 너무 높다. 끌고 가는 사람은 대개 빨리 지른다. 축을 더 넣어도 새 정보가 거의 안 늘어난다
OPN 개방성눈에 안 보인다. 누가 개방적인지는 며칠 같이 해야 알고 게임 한 판으론 안 드러난다
EMP 공감전원이 높게 답한다. "사람이 먼저 / 일이 먼저"에서 전자가 사회적으로 유리해 축이 안 갈린다

남긴 셋은 게임 한 판 안에서 눈으로 확인된다. 회의 5분이면 누가 끌고 가는지 보이고, 마감 때 계획형인지 드러나고, 갈등에서 직구인지 변화구인지 나온다.

8개가 한계다. 축을 4개 쓰면 16유형, 5개면 32유형이다. MBTI가 16개인데 그것도 이미 많다 — 대부분 자기 것만 알고 나머지는 모른다. 우리는 한 세션에 6명이 서로 유형을 보여주며 웃어야 하는데, 32개면 남의 유형이 뭔지 감이 안 온다. 8개여야 "아 쟤 그거구나"가 된다.

전용 3축은 유형에 안 쓰인다 — 그럼 어디에

① 궁합 계산      시너지 가중치 표에 9축 전부 들어감
② 칭호 일부      "팀의 평균값" "극단주의자"는 9축 전체를 봄
③ 리포트 서술    LLM이 인용하는 디테일 ← 실질적으로 가장 중요

같은 "선빵 불도저" 두 명

종훈   TP_DDL 1.0 막판 몰아서   TP_CFL 4.2 그 자리서 짚음   TP_ROL 4.5 맡음
민우   TP_DDL 3.8 나눠서 미리   TP_CFL 1.5 그냥 넘어감      TP_ROL 2.0 받쳐줌

→ 유형 이름은 같지만 리포트 본문은 전혀 다른 글이 나간다

4. 축당 2문항, 그중 1개는 역채점

5. 한 문항은 한 축만 잰다
   두 축을 동시에 재면 어느 쪽이 움직였는지 알 수 없다

게임 구성

공통 Stage 인터페이스

게임 담당이 가장 먼저 만들 것은 개별 게임이 아니라 이 인터페이스다. 이게 있으면 게임 추가가 하루에 여러 개 된다.
Stage
├─ id            : string
├─ frame         : "MANY" | "PAIR"
├─ category      : ("TP"|"MT"|"DY"|"NT")[]
├─ duration_sec  : int
├─ offline       : OfflineAction | null
├─ inputs        : 참가자에게서 무엇을 받나
└─ emits         : AxisDelta[] | LogEvent[]

AxisDelta                        LogEvent
├─ axis_id  : string             ├─ kind : "minority_pick" | "telepathy"
├─ source   : "BEHAVIOR"         │         | "me_too" | "guess" | "first_move"
│            | "IMPRESSION"      └─ payload : object
└─ delta    : float

모든 단계는 emits를 반드시 낸다.
아무것도 안 내는 단계는 게임이지 측정이 아니다. 넣지 않는다.

프롬프트 규칙 — 이 다섯 개를 반드시 넣는다

1. 넘겨받은 JSON에 있는 수치와 로그만 인용한다. 없는 사실을 만들지 않는다.
   ("회의에서 자주 발표하셨네요" 같은 문장 금지 — 그런 데이터가 없다)

2. 유형 · 칭호 · 궁합 등급은 이미 확정됐다. 바꾸지 않는다. 설명만 한다.

3. impression 값은 "팀이 본 나"다.
   "당신은 ○○입니다"로 쓰지 않는다. "팀은 당신을 ○○로 봤습니다"까지만.

4. 외모 · 성별 · 능력에 대한 문장을 만들지 않는다.

5. 개인 서술은 4~6문장. 궁합 이유는 1~2문장.
   수치를 최소 2개 인용한다. 인용 없는 뭉뚱그린 칭찬은 쓰지 않는다.

저장과 폴백

생성 성공 → DB 저장 → 이후 조회는 저장본만 읽는다
            └ 다시 부르지 않는다
            └ 매번 부르면 같은 사람 리포트가 매번 달라진다
            └ 어제 캡처한 것과 오늘 화면이 다르면 신뢰가 통째로 날아간다

생성 실패 → 유형별 템플릿 문구로 폴백
            └ 유형이 같으면 거의 같은 글이 나간다. 감수한다
            └ 축 · 칭호 · 궁합은 룰 기반이라 그대로 채워진다
            └ 리포트가 안 나오는 경우는 없다
